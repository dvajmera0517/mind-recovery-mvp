# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project scope

This is a **local MVP prototype** of a pharmacy-triggered nutrient-depletion recommendation engine. It covers **five medication classes**: metformin, statins, diuretics, PPIs (proton pump inhibitors), and glp1 (GLP-1 receptor agonists). It is **not connected to any real pharmacy system or patient data** — do not add integrations, network calls to external health/pharmacy APIs, or real patient data handling without explicit direction. Keep changes scoped to these five medication classes unless asked to expand scope.

The set of medication classes is `seed_data.py` — treat it as the single source of truth. Several places derive their class list from it dynamically specifically so adding/removing a class there is enough on its own: `main.SUPPORTED_CLASSES_MESSAGE`, `event_log.MEDICATION_CLASSES`, `scripts/demo.py`'s `MEDICATION_CLASSES`. A few places still need a manual touch when the class list changes, because they require real-world data this repo can't derive on its own — a RxClass/openFDA classification keyword (`rxclass.CLASS_KEYWORDS`, `openfda.SEARCH_QUERY_BY_MEDICATION_CLASS`) and a companion-page display name (`companion_page.MEDICATION_DISPLAY_NAMES`) — and `scripts/draft_content.py`'s `LLM_DRAFTABLE_CLASSES`/`SAMPLE_DRAFTABLE_CLASSES`, each deliberately narrower than the full class list since they're gated on an entry existing in `evidence_excerpts.py`/`sample_content.json` respectively, not on class membership alone.

## Tech stack

- Python 3.11+
- FastAPI (API layer)
- SQLAlchemy + SQLite (clinical content storage)
- Jinja2 + xhtml2pdf (printable companion page — HTML and PDF; xhtml2pdf was chosen over WeasyPrint because WeasyPrint needs native Pango/GObject libraries that aren't available in this dev environment)
- httpx (live outbound calls to USDA FoodData Central, RxClass, and openFDA) + python-dotenv (loads `FDC_API_KEY`/`ANTHROPIC_API_KEY` from a repo-root `.env`)
- anthropic SDK (Claude Opus 5) — LLM-assisted drafting for placeholder content, `scripts/draft_content.py` only; the main API server never imports it
- pytest + httpx (`TestClient`) for tests
- `src/` layout, packaged as `mind_recovery_mvp`, built with setuptools via `pyproject.toml`

## Setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env   # then fill in a real FDC_API_KEY — see below
```

`FDC_API_KEY` is **required**: the server fails fast at startup (not silently) if it's missing. Get a free key at https://fdc.nal.usda.gov/api-key-signup, or use USDA's public `DEMO_KEY` (rate-limited, no signup) to try things out.

## Run

```bash
uvicorn mind_recovery_mvp.main:app --reload
```

Health check: `GET http://127.0.0.1:8000/health`

## Test

```bash
pytest
```

Run a single test file: `pytest tests/test_health.py`
Run a single test: `pytest tests/test_health.py::test_health`

The default `pytest` run is fully offline — every USDA/RxClass/openFDA/Claude call is mocked (see `tests/conftest.py`'s autouse fixture for USDA/openFDA; the Claude call is mocked per-test in `tests/test_drafting.py`), and `-m "not integration"` (set in `pyproject.toml`) excludes the tests that hit real APIs. Run just those explicitly:

```bash
FDC_API_KEY=<your-key> ANTHROPIC_API_KEY=<your-key> pytest -m integration
```
(omit `FDC_API_KEY=` to fall back to USDA's `DEMO_KEY`. RxClass and openFDA don't need a key at all — `OPENFDA_API_KEY` is optional and only raises openFDA's rate limit. `ANTHROPIC_API_KEY` has no free/no-signup equivalent — the Claude integration test (`tests/test_drafting_integration.py`) skips itself with a clear message if it's not set, rather than failing.)

## Architecture

- `src/mind_recovery_mvp/main.py` — FastAPI app instance, lifespan hook (fail-fast `FDC_API_KEY` check, then DB init + seed load), and all routes. Entry point for `uvicorn`. Calls `load_dotenv()` at import time.
- `src/mind_recovery_mvp/models.py` — `NutrientContent` SQLAlchemy model (one row per medication class).
- `src/mind_recovery_mvp/seed_data.py` — the verbatim clinical content for the five seeded medication classes (metformin, statins, diuretics, ppi, glp1). This is the single source of truth for clinical content *and* for the set of valid medication classes (see "Project scope" above) — null fields there are intentional (content not yet drafted/cited by a pharmacist) and must stay null, never filled in with invented text. metformin is the only record with `content_origin: "pharmacist_authored"` set — it never went through the draft/review pipeline; the other four are `content_origin: None` until `draft_content.py` tags them.
- `src/mind_recovery_mvp/loader.py` — idempotent seeding of `seed_data.py` into the DB, run on startup.
- `src/mind_recovery_mvp/db.py` — SQLAlchemy engine/session setup and the `get_db` FastAPI dependency.
- `src/mind_recovery_mvp/schemas.py` — Pydantic request/response models.
- `src/mind_recovery_mvp/usda.py` — real, live USDA FoodData Central enrichment for every food in `foods_that_may_help`, on every `/fill-event` call. Two distinct failure modes, handled differently on purpose: a **missing `FDC_API_KEY`** is a startup-time config error (loud — see `main.lifespan`); a **single food's lookup failing** at request time (timeout, rate limit, 5xx, malformed response) is caught per-food and degrades to `nutrients: None` for that one food (quiet — falls back to the plain food name, never raises, never blocks the response). Search results are restricted to `dataType=Foundation,SR Legacy` (generic whole-food entries) — without that filter, USDA's relevance search also matches branded products by name (e.g. a candy bar literally named "EGGS" outranked actual eggs for the query "eggs"). Category terms like "dairy" or "fish" still won't necessarily map to an intuitive specific food — that's a real limitation of a single-query lookup against a food database, not a bug to silently paper over.
- `src/mind_recovery_mvp/rxclass.py` — `classify_medication_class(drug_name)`, called by `POST /simulate-prescription` (see below), looks up a drug's therapeutic class via NLM's RxClass API (`getClassByRxNormDrugName`, no key needed) and maps it to one of the target classes via `CLASS_KEYWORDS` (a manually-maintained keyword per class — new medication classes need an entry added here, verified against a live RxClass call for a representative drug, since the right keyword/classification-system isn't guessable from the class name alone). Scans every classification system RxClass returns (EPC, ATC, VA, MOA, ...), not just EPC — e.g. the potassium-sparing diuretic spironolactone is EPC-classified as "Aldosterone Antagonist" (no "diuretic" in that name at all), and only shows up as a diuretic under VA/ATC. glp1's keyword (`"glp-1 receptor agonist"`) was verified live against semaglutide/liraglutide/dulaglutide — all three come back with a consistent `EPC -> GLP-1 Receptor Agonist`. Returns `None` for a drug that doesn't map to any target class — a normal, expected outcome for most real-world drug names, not a failure, and callers should treat it that way (see `simulate_prescription.py`).
- `src/mind_recovery_mvp/openfda.py` — `get_fda_label_reference(medication_class)`, called unconditionally on every `/fill-event`. Pulls `drug_interactions` and `warnings_and_cautions` from a representative FDA drug label via openFDA and attaches them as `fda_label_reference` — a **separate top-level field**, not nested under `recommendation`, since it's raw FDA label text, not pharmacist-curated content. `OPENFDA_API_KEY` is optional (raises the rate limit if set; unlike `FDC_API_KEY` it's not required to start). Same fail-soft contract as `usda.py`: any failure degrades the whole thing to `None` rather than raising. `SEARCH_QUERY_BY_MEDICATION_CLASS` is manually-maintained per class, same reasoning as `rxclass.CLASS_KEYWORDS` above. Real-world quirks worth knowing: (1) `statins`/`diuretics`/`ppi`/`glp1` are class names, not queryable ingredient names in openFDA, so those query by a representative drug's `pharm_class_epc` instead (the same EPC vocabulary `rxclass.py` uses, e.g. `"GLP-1 Receptor Agonist [EPC]"`, verified live) — metformin queries directly by name, but as an *exact* match on the bare ingredient (`openfda.generic_name.exact:"METFORMIN"`), because a plain substring search also matches combination products like "SITAGLIPTIN AND METFORMIN HYDROCHLORIDE" and those can outrank plain metformin's own label; (2) some FDA labels use the older `warnings` section instead of the newer `warnings_and_cautions` split — falls back to it rather than reporting no warnings when they're just filed under the other name.
- `src/mind_recovery_mvp/evidence_excerpts.py` — short, paraphrased, non-verbatim source material for statins/diuretics/ppi/glp1 (data only, not prose in code), used exclusively as `drafting.py`'s (`--use-llm`) input. Not a clinical database and not citation-ready — `citation_label` is carried forward verbatim as `clinical_source`, never turned into a more specific invented citation. `draft_content.py`'s `LLM_DRAFTABLE_CLASSES` is derived from this file (a class is LLM-draftable exactly when it has an entry here) — if a 6th class is ever added to `seed_data.py` without also adding an evidence excerpt here, `--use-llm` stays unavailable for it, which is correct: don't add an excerpt without being given real source material to paraphrase from.
- `src/mind_recovery_mvp/sample_content.py` + `sample_content.json` — hand-written, finished demo copy for the same four classes (data in the `.json`, not prose in code), the **default** drafting path (see `scripts/draft_content.py` below): no API call, no key needed. `apply_sample_content_to_record(...)` writes it onto a `NutrientContent` row, setting `content_status = STATUS_SAMPLE_CONTENT_PENDING_REVIEW` and `content_origin = CONTENT_ORIGIN_SAMPLE` — never `approved`, and `evidence_excerpt` is left null (there's no excerpt; it's hand-written directly). `draft_content.py`'s `SAMPLE_DRAFTABLE_CLASSES` is derived from this file the same way `LLM_DRAFTABLE_CLASSES` is derived from `evidence_excerpts.py`.
- `src/mind_recovery_mvp/content_review.py` — the shared status vocabulary and logic `drafting.py`, `sample_content.py`, `companion_page.py`, and `scripts/review_content.py` all depend on: `STATUS_LLM_DRAFTED_PENDING_REVIEW`/`STATUS_SAMPLE_CONTENT_PENDING_REVIEW`/`STATUS_APPROVED`/`STATUS_APPROVED_WITH_EDITS`, `PENDING_REVIEW_STATUSES` (the set of both pending statuses — what `review_content.py` lists and what `is_customer_visible` hides), `CONTENT_ORIGIN_PHARMACIST_AUTHORED`/`CONTENT_ORIGIN_LLM`/`CONTENT_ORIGIN_SAMPLE`/`CONTENT_ORIGIN_LABELS` (provenance, tracked separately from `content_status` since that alone no longer distinguishes sample vs. LLM once a record is `approved`; each `CONTENT_ORIGIN_LABELS` value is the *complete* "Content origin: ..." text, not a description with a shared suffix appended in code — pharmacist-authored content gets no "pharmacist-reviewed" claim, since nothing was reviewed, while both draft paths do), `is_customer_visible(content_status)` (the render gate — see below), and `approve_record(...)` (sets status/reviewer/timestamp; edits vs. no edits decides `approved` vs. `approved_with_edits`, comparing new values so resubmitting an unchanged value doesn't count as an edit). When the sample-content mode was added, `is_customer_visible` and `review_content.py`'s query both turned out to hardcode the single LLM status rather than genuinely matching "any pending-review status" as assumed — fixed by introducing `PENDING_REVIEW_STATUSES` as the actual shared set both now check against; `tests/test_content_review.py::test_pending_review_statuses_covers_both_draft_paths` is the regression test for this.
- `src/mind_recovery_mvp/drafting.py` — `draft_content_fields(...)`, a real, live call to Claude (`claude-opus-5`, via `client.messages.parse(..., output_format=DraftedFields)`) that drafts `why_it_matters`/`foods_that_may_help`/`supplements_to_discuss`/`talk_to_pharmacist_if` from ONLY the matching `evidence_excerpts.py` entry — the system prompt explicitly forbids adding claims beyond the excerpt and requires `null` over inventing a plausible-sounding value. `clinical_source` in the returned dict is always `citation_label` verbatim, enforced in code after the call — never trusted from the model output, even though the prompt also asks the model to carry it forward. `apply_draft_to_record(...)` writes a draft onto a `NutrientContent` row, always setting `content_status = STATUS_LLM_DRAFTED_PENDING_REVIEW` (never `approved`) and `content_origin = CONTENT_ORIGIN_LLM`, and keeping `evidence_excerpt` attached for review. `ANTHROPIC_API_KEY` is a parameter here, not read from env internally — `scripts/draft_content.py`'s `--use-llm` path is the only place that reads it from the environment and is the only place that fails fast if it's missing; the main API server never imports this module, and neither does the default sample-content drafting path.
- `src/mind_recovery_mvp/companion_page.py` + `src/mind_recovery_mvp/templates/companion_page.html` — renders the printable companion page (single Jinja2 template drives both the HTML and PDF endpoints, so there's one source of truth for the markup). Any null clinical field renders as a visible "Pending pharmacist review" callout, never blank. Rendering is also gated on `content_review.is_customer_visible(record.content_status)`: for `PLACEHOLDER` and either pending-review status, all 5 non-medication/non-nutrient-concern fields are forced to the pending callout **even if the underlying DB values are populated** — e.g. diuretics' `PLACEHOLDER` record has a non-null `foods_that_may_help` in the seed data, but it still renders as pending, because drafting, loading sample content, or partial seeding doesn't change what's safe to show a customer. Only `approved`/`approved_with_edits` render real content (with the original per-field null→pending fallback still applying underneath), and — only then — a provenance line printed directly on the page (both HTML and PDF, not just stored as data): `"Content origin: {label}"` where `{label}` comes verbatim from `content_review.CONTENT_ORIGIN_LABELS[record.content_origin]` (omitted entirely if `content_origin` is null — a defensive fallback for a hypothetical future draft path that forgets to tag it, not a real case today, since `seed_data.py` sets metformin's `content_origin` to `"pharmacist_authored"` explicitly). Metformin's own pre-existing status (`"drafted — needs final pharmacist/legal sign-off"`) intentionally falls through the visibility gate as visible — it predates this pipeline, and `review_content.py` never lists it either, so gating it here with no way to un-gate it would strand it. See `content_review.is_customer_visible`'s docstring for the full reasoning — this was a judgment call, not something explicitly spelled out in every case by the original requirements, so it's worth rereading if this behavior ever looks wrong.
- `src/mind_recovery_mvp/event_log.py` + `FillEventLog` model (`models.py`) — records one row per `/fill-event` call (timestamp, medication_class); `companion_page_requested` is flipped `True` on the most recent log row for that class when a companion page is subsequently requested. There's no session/request correlation in this MVP, so "subsequent" means "most recent fill-event for that medication_class," not a specific caller. `GET /metrics` aggregates this into per-class counts — an explicit stand-in for the real purchase-lift/engagement measurement described in the MVP plan, not the real thing (the response's `note` field says so too). `POST /simulate-prescription` does **not** write to this log — it's a different kind of operation (drug-name classification, not a medication-class-scoped pharmacy fill) and wasn't asked to feed into engagement metrics.
- `src/mind_recovery_mvp/simulate_prescription.py` — `run_simulation(drug_name, db, fdc_api_key)`, backing `POST /simulate-prescription`. Orchestrates `rxclass.classify_medication_class` → (if matched) the same `NutrientContent` lookup `main._get_record_or_404` does, `usda.enrich_foods`, and `openfda.get_fda_label_reference` — all three called via qualified module references (`rxclass.`/`usda.`/`openfda.`, not `from ... import <function>`), the same reason `main.py` calls `openfda.get_fda_label_reference(...)` qualified: it's what lets `tests/conftest.py`'s autouse mocks actually intercept the calls regardless of how this module gets imported elsewhere. Every one of the three calls is wrapped in `_timed_call`, which returns `(result, elapsed_ms)` via `time.perf_counter()` — the response's `timing_ms` block exists specifically so a caller can see these are real, non-instant network calls rather than trust that claim blindly (verified live: a real metformin lookup showed `~562ms`/`~847ms`/`~323ms` for RxClass/USDA/openFDA respectively). An unmatched drug name (`classify_medication_class` returns `None`) short-circuits before USDA/openFDA are even attempted — `timing_ms.usda`/`.openfda` are `null`, not `0`, to distinguish "not attempted" from "attempted and took no time." If RxClass matches a class that somehow isn't in the seeded seed_data.py (shouldn't happen — `rxclass.CLASS_KEYWORDS` and `seed_data.py` are meant to stay in sync), that's treated as a genuine data-integrity bug (raises, surfaced as a 500) rather than silently reported as "unmatched," since reporting `matched: false` there would misrepresent that classification actually succeeded.
- `tests/conftest.py` — shared `client` fixture: a `TestClient` wired to an isolated temp-file SQLite DB (via `app.dependency_overrides[get_db]`), pre-loaded with the seed data. Also has an autouse fixture that sets a placeholder `FDC_API_KEY` and mocks `usda.lookup_food_nutrients`, `openfda.get_fda_label_reference`, and `rxclass.classify_medication_class` (default fake: `"statins"`, matching `FAKE_RXCLASS_RESULT`) for every test *except* ones marked `@pytest.mark.integration` — that's what keeps the default `pytest` run offline without every test file needing to mock these itself. Note `main.py` and `simulate_prescription.py` both import the `openfda`/`rxclass`/`usda` modules (`from mind_recovery_mvp import openfda`, etc.) and call them qualified, rather than importing the functions directly — a direct `from ... import get_fda_label_reference` would bind the caller's own reference at import time, and patching `mind_recovery_mvp.openfda.get_fda_label_reference` afterward wouldn't affect what the caller actually calls.
- `tests/test_usda_integration.py`, `tests/test_rxclass_integration.py`, `tests/test_openfda_integration.py`, `tests/test_drafting_integration.py`, `tests/test_simulate_prescription_integration.py` — the tests that hit real APIs; excluded by default, see Test section above. The Claude one skips (doesn't fail) if `ANTHROPIC_API_KEY` isn't set, since there's no public testing key to fall back to. It exercises `drafting.draft_content_fields` directly (the `--use-llm` code path), not the CLI script. `test_simulate_prescription_integration.py` runs `/simulate-prescription` for a real matched drug (`"metformin"` — chosen specifically because it has foods to enrich, so all three APIs get genuinely exercised, not just two) and a real unmatched one (`"amoxicillin"`).
- `scripts/draft_content.py` — CLI: `python scripts/draft_content.py <statins|diuretics|ppi|glp1> [--use-llm]`. Default (no flag) loads `sample_content.py`, no key needed. `--use-llm` calls `drafting.draft_content_fields`/`apply_draft_to_record` and requires `ANTHROPIC_API_KEY`, failing fast with a clear message if it's missing, before touching the DB. Class-choice validation differs by mode: default mode validates against `SAMPLE_DRAFTABLE_CLASSES` (derived from `sample_content.json`), `--use-llm` against `LLM_DRAFTABLE_CLASSES` (derived from `evidence_excerpts.py`) — currently the same four classes for both, but they're allowed to diverge (e.g. a class could get an evidence excerpt without sample content, or vice versa).
- `scripts/review_content.py` — interactive CLI: `python scripts/review_content.py`. Lists every record whose status is in `content_review.PENDING_REVIEW_STATUSES` (both LLM-drafted and sample-content pending), shows the draft next to its source (`evidence_excerpt` for LLM drafts; "hand-written sample content (no evidence excerpt)" for sample drafts — the label is conditional on whether `evidence_excerpt` is set, not on `content_origin`, so it stays correct even for hypothetical future draft paths), and lets the reviewer approve as-is, edit fields first, or skip. Reviewer name comes from `REVIEWER_NAME` env var if set, else an interactive prompt. Thin wrapper around `content_review.approve_record`; `content_origin` is left untouched on approval, on purpose.
- `scripts/demo.py` — `python scripts/demo.py`, the single command demonstrating the whole before/after drafting-and-review story, zero API keys required. Renders all five companion pages to `./output/before_review/` exactly as seeded, drafts sample content for the four non-metformin classes and reviews them via `scripts/draft_content.py`/`scripts/review_content.py` **run as real subprocesses** (not re-implemented inline) sharing one `env` dict (`DATABASE_URL` points all three subprocesses — server, draft, review — at the same scratch `output/demo.db`) so this exercises the actual CLI scripts a person would run, not a simulation of them. The review step feeds `review_content.py`'s interactive prompts non-interactively via `subprocess.run(..., input="a\n" * len(DRAFTABLE_CLASSES))`, approving everything as-is, with `REVIEWER_NAME` forced to `"Demo Reviewer (not a licensed pharmacist)"` — printed inside `!`-banner lines in the console output specifically so it reads as a stand-in, not a real review. Re-renders all five pages to `./output/after_review/`, then prints a before/after `content_status` table and a `10/10 PDFs` confirmation (5 classes × before/after).
- `tests/test_startup.py` — tests the fail-fast `FDC_API_KEY` check. Note: a bare `TestClient(app)` (what the shared `client` fixture yields) never runs FastAPI's lifespan hook — only `with TestClient(app):` does — so this is the one place in the suite that uses the context-manager form deliberately.
- `tests/` — pytest suite, uses FastAPI's `TestClient` against the `app` object directly (no live server needed to run tests).

## No schema migrations

`db.init_db()` only calls `Base.metadata.create_all()`, which creates missing *tables*, not missing *columns* on an existing one. There's no Alembic or other migration tooling (deliberately, to stay simple for an MVP). If `NutrientContent` gains a new column (as it did in stage 11: `evidence_excerpt`, `reviewed_by`, `reviewed_at`, then `content_origin`) and you have a pre-existing local `mind_recovery.db` from before that change, delete the file and let it get re-created — `*.db` is gitignored, so no real data is ever at stake here.

## Known dev-environment quirk

In some sandboxed shells, `pip install -e .` editable installs are not picked up by fresh Python processes (the `.pth` file exists and is correct, but isn't processed) — `pytest`/`uvicorn` then fail with `ModuleNotFoundError: No module named 'mind_recovery_mvp'` even though `pip show` confirms the install. If this happens, run with `PYTHONPATH=src` prefixed (e.g. `PYTHONPATH=src pytest`, `PYTHONPATH=src uvicorn mind_recovery_mvp.main:app --reload`). This is specific to that shell environment, not a project misconfiguration — a normal terminal does not need this workaround.
